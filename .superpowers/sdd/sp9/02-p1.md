## 一、实测校正 —— spec §5.1 与后端实际不符的地方

全部 curl 实证 / 读 Go 源码核对过。**这一节是本期最值钱的产出,后续期直接引用。**

### 1. 同一个 `/v1/gateway/*` 前缀下,信封层数按端点不同

```
GET /v1/gateway/port          → {"success":200,"message":"ok","data":"80"}     有信封,data 是字符串
GET /v1/gateway/ssl           → {"success":200,...,"data":{...}}               有信封
GET /v1/gateway/components    → {"components":[...]}                           ← 裸 JSON
GET /v1/gateway/device-info   → {"hostname":"NimoOS","os":"nimoos",...}         ← 裸 JSON
```

后两个**不能套 `unwrap()`**,套了必抛。记忆库「核字段名≠核信封层数」的同一个坑。

### 2. 命名陷阱(spec 已警告,这里给实测值)

| Vue2 方法 | 真实端点 | 包内新名 |
|---|---|---|
| `getVersion()` | `GET /v1/sys/os_version` | **`getOsVersion()`** |
| `getAppVersion()` | `GET /v1/sys/version` | **`getAppVersion()`** |

包里原有的 `getVersion()` 打 `/sys/version`,语义等于 `getAppVersion()` → 保留成 deprecated 别名(SP1 起有调用方)。

**Vue2 的行标签与数据源是交叉的**:标签「固件更新」的行副标题取 `hardware.version`、数据用 `os_version`;标签「系统更新」(源码注释写 App Update)副标题取自己的 `current_version`、数据用 `version`。**1:1 照留,别"纠正"。**

### 3. `/v1/sys/update` 与 `/v1/sys/os_update` 失败时也返回 HTTP 200

错误只写在信封里(`NimoOS/route/v1/system.go:93-102` 与 `:149-158`,错误分支都是 `ctx.JSON(common_err.SUCCESS, Result{Success: SERVICE_ERROR, ...})`)。axios 不会 reject,**必须自己查信封**。

Vue2 的 `UpdateModal.updateSystem()` 是查 `res.data.success !== 200` 的 —— 不查等于比 Vue2 更糟。
对比:`/gateway/port` 与 `/gateway/ssl` 的写操作返回真实 4xx/5xx,axios 自己 reject;`/sys/download/cancel` 无失败分支(恒 SUCCESS)。

### 4. 其它实测形状

- `GET /v1/usb/usb-auto-mount` → `data` 是**字符串** `"True"`/`"False"`,不是布尔(已在包里归一)
- `GET /v1/gateway/port` → `data` 是**字符串** `"80"`
- `/v1/gateway/ssl` 未签发时两个时间是 Go 零值 `0001-01-01T00:00:00Z`
- `/sys/hardware` 本机 `hardware_name` 与 `drive_model` 都是**空串** → 消费方必须有回退
- `PUT /v1/sys/state/{state}` 只认 `off`/`restart`,**其它值也返回 200 但什么都不做** → 包里把参数收窄成字面量联合
- `trigger_download=1` 是**查询参数**,下载不是独立端点
- **`GET /gateway/port` 没有挂 JWT 中间件、CORS 是 `*`** → 换端口后用不带 token 的裸跨源 `fetch` 探新端口是可行的(终审复核 Gateway Go 源码确认)

### 5. spec 方法表漏了 2 个 UpdateModal 必需的

`updateOs()` → `POST /v1/sys/os_update`、`cancelDownload()` → `POST /v1/sys/download/cancel`。

## 三、移植纪律登记 —— Vue2 的 bug 不照抄(共 7 条)

| # | Vue2 的问题 | 本期改法 |
|---|---|---|
| 1 | **挂载即回写配置**:`getConfig()` 塞进 `barData` 触发深度 watcher → 立刻把刚读到的原样写回,每次打开设置都白写一次 | 不设深度 watcher;只在用户操作时显式 patch |
| 2 | **挂载即下发磁盘待机指令**:`disk_standby` watcher 在 hydrate 时也 fire | 只在用户改选时下发 |
| 3 | **`system` blob 丢写竞态**:Vue2 整块覆写,而 New-UI 的 locale store 也在同一个 key 上读改写 | `systemConfig.ts` 模块级 Promise 串行队列 + 队列内重新读取;单次失败不卡死队列 |
| 4 | **端口探活定时器泄漏**:只在成功时 `clearInterval` | 上限 40 次≈60s,超时停表提示;卸载也停 |
| 5 | **换端口后跳根路径**(= 旧 Vue2 应用) | 保留 `pathname + hash`,留在新 UI 当前页 |
| 6 | **电源探活被认证拦截器劫持**:走带 401 刷新的 axios,重启期间一个 401 就清 token 跳登录、打断整个流程 | 裸 `fetch`,**任何 HTTP 响应(含 401/500)都算服务器活着**,只有网络错误才算下线 |
| 7 | **初次异步加载盖掉用户已做的修改**:各行 `onMounted` await 完再赋值,真机有网络往返时会把用户刚做的操作"抹回去" | 每个组件就地一个 `touched`/`editedDuringLoad` 布尔,赋值前自查。**不抽公共 guard**(评审判定过早抽象)。回归测试必须走**交错**路径 |

> **纪律 #7 是本期最高频的返工来源** —— 计划里只写了 Task 5 的两个组件,实际适用 7 个组件,后面几期(Task 6/7/11)都是实现者主动补上并被评审确认。**新增任何"onMounted 取值 → 赋给本地 ref"的组件都要带这个守卫。**

### 交错测试的两个空转陷阱(都真实踩过)

1. **先 await 完加载再改控件** —— 证明不了任何事。必须用可手动 resolve 的 deferred 卡住加载,期间改控件。
2. **"旧快照"是在用户操作**之后**从共享 mock state 里读的** —— 那它已经是新值了,没有守卫测试也会过。快照必须在操作**之前**拍。

## 八点五、⚠️ 浏览器自查 **0/16 未完成** —— 阻塞在认证,不是没做

任务门(测试/tsc/build)全绿,但**16 项视觉自查一项都没做成**。也就是说:**到目前为止没有任何人真正"看过"这个屏幕。**

**根因(curl 实证,不是猜)**:
```
curl http://127.0.0.1:80/v1/sys/hardware                                  → 200 真实数据
curl http://127.0.0.1:80/v1/sys/hardware -H "Authorization: Bearer 假的"  → 401
```
`NimoOS-Common/utils/jwt/jwt_helper.go` 的 `Skipper` 是 `c.RealIP()=="127.0.0.1"` —— **localhost 免鉴权的前提是完全不带 `Authorization` 头**;一旦带了(哪怕是假的)就走真校验并 401。而共享包 `NimoOS-Service/src/http.ts` 的请求拦截器只要 `localStorage.access_token` 非空就在每个请求上挂 `Authorization`。

于是 P0 那套「往 `public/` 放个 HTML 写假 token」的手法**在 P1 失效**:假 token 能骗过 `router/guard.ts` 的存在性检查进到 `/settings/general`,但页面一 mount 就发真实 API → 401 → 用假 refresh_token 刷新也失败 → `onAuthFail` 清 token 跳登录页。**虚拟时间预算调到 50ms 都已经在登录页了**,没有可截图的时间窗口。

> **P0 能用是因为 P0 那批组件(壳/rail/骨架)不发鉴权请求。这个手法从 P1 起对任何真的调后端的页面都不再可用 —— 后续期别再照抄。**

**执行者没做、也不该做的**(判断正确,记录在此以免后人重走):没有猜/翻默认密码;没有跑 `nimoos-user-service --ru --user <name>`(那会真的改掉这台 NAS 现行管理员密码,属机主拍板范围);没有探内部端口或 dump 环境变量找 token。

**要补做只有两条路,都得机主本人**:
1. 机主在真实浏览器登录一次,把 devtools 里 `localStorage.getItem('access_token')` 的值给下一个执行者 → 用真 token 重跑同一套截图流程(**推荐,零副作用**)。
2. 机主自己用浏览器把 16 项过一遍(反正实机验收本来就是机主的活,只是范围从「3 条破坏性路径」扩大到「全部」)。
