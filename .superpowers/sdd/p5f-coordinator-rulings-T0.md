## 一、两个 `NEEDS_CONTEXT` 的裁定

### R1 —— N-1 `kw-*` / `kr-*` 不被 `NEW_RE` 认:**批准方案 B**(`WHITELIST_425` / `NON_K_HELPER_CLASSES` 20)

**事实**:`NEW_RE` 的 `k(?:2|n)?-` 分支只接受 `k-`/`k2-`/`kn-`;`kr-` 的 `r` 与 `kw-` 的 `w` 都不匹配
⇒ **41 个 `kw-*` + 9 个 `kr-*` + `cur` = 51 个类**会一次性掉进 `nonKClassNames`,打红那条集合相等断言。
**T0 与评审各自独立算出同一组数字**(A:375/70 · B:425/20)。

| | 方案 A | **方案 B(采纳)** |
|---|---|---|
| 做法 | 不动 `NEW_RE`,51 个类全进 `NON_K_HELPER_CLASSES` | **给 `NEW_RE` 加 `kr-` / `kw-` 分支** + 进 `WHITELIST` + 加排除条件 |
| `WHITELIST` | 375 | **425** |
| `NON_K_HELPER_CLASSES` | 70 | **20**(19 + `cur`) |

**裁定理由(三条,评审已独立复核)**:
1. 🔴 **`fb-*` / `nme-*` 是逐字同款先例** —— P5c-T2a 从 `<style scoped>` 搬 8 个 `fb-*` 类时,
   做法**正是**「加 `NEW_RE` 分支 + 进 `WHITELIST` + 加排除条件」三件套。
   **本期 `kr-*` 与 `fb-*` 的来源完全同构**(都是从某个 `.vue` 的 `<style scoped>` 搬进 `knowledge.scss`)。
   ⇒ **方案 B 才是本仓既定做法**;按 **R18** 口径,**既定做法优先于 brief/计划书的字面假设**。
2. **`NON_K_HELPER_CLASSES` 那条断言的原文用途就是「防清单变垃圾桶」**(逐个登记出处的小表)。
   把 51 个知识库命名空间的类倒进去 = **亲手把它变成垃圾桶**,且它们从此不再受
   「没有搬多」白名单扫描的覆盖 = **净减少守卫覆盖面**。
3. **扩 `NEW_RE` 是加固不是放宽**(§9.10):它让扫描**多认 51 个类**,`old ⊆ new` 已由 T0 预跑、评审复跑,零逃逸。

🔴 **落地判据(T2 逐条自证,评审逐条复核)**:
1. **常量名跟着数字改**:`WHITELIST_348` → **`WHITELIST_425`**(本档习惯);`NON_K_HELPER_CLASSES` = **20**。
2. 🔴 **严格超集自证**:程序化证明「旧 `NEW_RE` 能匹配的每一个串,新 `NEW_RE` 都能匹配」——
   `old ⊆ new` 且 `new ⊋ old`。**自我声明不算证明。**
3. 🔴 **必须同步改 `knowledgeStyles.test.ts:297-305` 那条硬编码 `OLD_RE`/`NEW_RE` 的超集自证**
   (**评审补充的、T0 没写的一条**)—— **不改它,那条自证就变成空壳**(它比的是两个旧常量)。
   **判据:改完后把新分支从被测正则里删掉 → 那条自证必须报红。**
