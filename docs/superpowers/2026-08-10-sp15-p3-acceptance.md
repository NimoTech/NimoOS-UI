# SP15-P3 真机验收清单（相册区时间线性能线）

> 分支 `sp15-photos-moments`，代码末位见文末「六道门」一节。**未部署、未推 origin、未合 master。**
> 这一期**没有 1:1 靶子**（Vue2 没有这套分桶时间线机制），验的是**机制在跑**，不是「界面长得
> 像不像」。

---

## 开始之前必读（不读会把正常当缺陷）

**第 1–4 步需要机主已经把 `NimoOS-Photos` 升级到 origin/main 并部署**（本文写作时机主提供的
信息：`/usr/bin/nimoos-photos` 已在 2026-08-10 18:48 构建，二进制里含 `/timeline/buckets` 与
`/timeline/bucket` 两个新接口）。如果还没升级/部署后端，**第 1–4 步现在验不出预期结果**，
只能先验第 5 步。

**第 5 步是"老后端兜底"这条路径**，只有在后端**没有**这两个新接口时才能观察到"探测失败 →
退避 10 分钟"这套行为。**一旦后端升级部署完，这条路径就再也回不去了**——本文写作时机主
已经在部署新后端，所以第 5 步**在这台设备上今后不再可验**。这不是缺陷，是这条验收路径
本身的性质：它验的是"新老交替瞬间"，交替一旦完成就没有回头路，除非专门装一个老版本
二进制。**如实说明，不要为了凑够步骤数硬写一个验不出来的第 5 步。**

**这台设备的相册库很小**：`/DATA/Gallery` 只有 14 个媒体文件，缩略图/资产缓存目录约 785
个资产。**不会看到"变快"**——本期的价值不是"从慢变快"，而是"从一次性拉全部（几百 KB～
几 MB 的 JSON、几十上百张图）变成按月分批拉、按可视区域分批渲染"。库这么小，两种做法在
肉眼观感上几乎没有差别，**验收验的是背后请求/DOM 的机制有没有真的按分桶方式在跑**，
不是秒表。

**部署后端之后，如果打开相册页看起来还是老样子**（一次性网络请求、没有分月骨架）：
先做一次**硬刷新**（`Ctrl-Shift-R`）。目录探测失败后有 **10 分钟退避**（见 §5.5），如果
你是在后端刚部署之前访问过这台设备的相册页，浏览器里跑着的那次 JS 还记得"10 分钟内不用
再探测"，需要重新加载页面才会重新探测一次。

## 验收步骤

### 1. 目录只请求一次，首屏立刻出现月份骨架

点击路径：打开 F12 DevTools → Network 面板 → 过滤框输入 `timeline` → 清空面板 →
左侧全局导航 → **相册**（`/app/#/photos`）。

- [ ] Network 面板里 `timeline/buckets` **只出现一次**（不应该每次滚动都重新拉目录）
- [ ] 页面**立刻**（不是等一两秒白屏之后）出现若干个**月份标题行**（形如"2026年8月"）+
      每行右边的**张数**（`.month-count`）+ 下面一块**等高的灰色占位块**（骨架，会有一道
      流光扫过），不是整页空白
- [ ] 如果这台设备相册一张照片都没有，改为验证"空状态"文案出现，不算失败

### 2. 慢慢往下滚：逐月请求，滚过的月份不重复拉

点击路径：接第 1 步的页面 → Network 面板保持 `timeline` 过滤 → **慢慢**向下滚动相册网格
（滚一点、停一下、再滚，给请求时间发出去）。

- [ ] 每当一个新的月份骨架块进入可视区域附近，Network 面板里就出现一条新的
      `timeline/bucket?year=..&month=..` 请求
- [ ] 那个月份的骨架灰块随后变成真实的照片瓷砖（如果那个月确实有照片）
- [ ] 滚回**已经加载过**的月份（比如滚到底部又往回滚一点），**不会**再看到该月份重复发
      `timeline/bucket` 请求——它已经在内存里了

### 3. 滚很远再滚回顶部：远处的瓷砖被卸载，滚动条不跳

点击路径：接第 2 步的页面 → 打开 F12 → **Elements** 面板 → 用 `Ctrl+F`（Elements 面板内的
搜索框）搜索 `class="tile"` 看数量，或者直接在 Elements 树里找 `.photos-grid`/月份容器 →
把相册页滚动条**拖到最下面** → 再**拖回最上面**。

- [ ] 滚到最下面时，Elements 里当前"实际渲染的 `.tile` 元素数量"**没有**等于全库所有已加载
      照片之和——远离可视区域的月份，其瓷砖应当被卸载（数量会随滚动位置**有增有减**，
      不是单调递增到底）
- [ ] 因为本机库很小（14 个媒体文件），如果所有月份加起来凑不满一屏，这条可能观察不出
      明显差异——这种情况下改为确认："滚动本身流畅、没有卡顿，滚动条位置没有跳动/回弹"
- [ ] 滚动条来回拖动的过程中，**滚动条位置本身不会跳变**（比如滚到一半突然跳到顶部或
      底部——这种情况才是缺陷）

### 4. 收藏页 / 回收站页：分页 + 精确总数 + 未取完的降级提示

点击路径：左侧全局导航 → 相册 → 顶部或侧边找到「**收藏**」入口（`/app/#/photos/favorites`）。

- [ ] 页面顶部计数（`{{ N }} 张照片` 一类文案）显示的是一个具体数字——这是通过
      `listFavoriteIds` 另外取的**精确总数**，不是"首屏 500 条"这个数
- [ ] 如果收藏总数**超过 500**：往下滚到底部，出现「**加载更多**」按钮；点击后继续加载
      下一批；**在还没取完全部收藏之前**，统计卡片/年份分布旁边会出现一行小字
      「**统计基于已加载的前 N 项**」——这一行**只在未取完时出现**，取完后消失
      （用 DevTools 的 Network 节流成慢速网络，趁"加载更多"进行中截图能更容易验证这个提示）
    - 本机收藏数如果不足 500，这一段整体验不出来——改为确认「加载更多」按钮**不出现**
      （因为已经一次性取完了），这是预期，不是缺陷
- [ ] 回收站页（`/app/#/photos/trash`）同理：滚到底部若出现「加载更多」，点击后继续加载；
      未取完时同样有「统计基于已加载的前 N 项」提示
- [ ] **回收站的批量操作要点一次**：点「**恢复全部**」或「**清空最近删除**」——
      如果此刻**还有没加载完的页**，界面会先把剩余页悄悄拉完，再弹出确认框；
      确认框里的数字必须是**准确的全量总数**，不能是"当前已加载的这一批"这种偏小的数字
    - ⚠️ 这两个操作是真实的批量动作，**点确认前请三思**：「恢复全部」会把回收站清空、
      「清空最近删除」是**永久删除、不可恢复**。如果不想真的执行，弹出确认框后点
      「取消」即可，前半段（数字准不准）已经验完了

### 5. 后端未升级时的老接口回退（本文写作时刚好是这台设备的状态，随时会因为部署失效）

> 见开头「必读」——这一步只在后端**还没有** `/timeline/buckets` 接口时才能验，机主一旦
> 部署新后端，这条路径就消失了，**不要在部署后再来找这一步**。

点击路径：（后端仍是旧版本的前提下）左侧全局导航 → 相册。

- [ ] 页面正常显示相册（走的是老的 `/timeline` 整表接口，不是分桶）
- [ ] F12 Network 里能看到一次 `timeline/buckets` 请求返回 **404**
- [ ] 之后 **10 分钟内**刷新页面/重新进入相册页，**不会**再看到 `timeline/buckets` 请求
      （前端记住了"最近探测过、还没到退避期"，直接走老接口，省掉一次注定失败的请求）
